- 编辑/预览/readiness 使用 dynamic resolve。
- Prepare/Start 使用 frozen Production Snapshot。
- Krea2/H3 只接收 ResolvedShotContext 或既有 GenerationValues。
- Preparation 复用 ProductionQueueService、ProductionOrchestratorService、ProductionBatch、ProductionRun。
- 不新增 NewProductionExecutor、SecondQueue、SchedulerService。

## 7. Ten Architecture Decisions

1. Profile vs Asset：Profile 表达语义身份和规则；Asset 表达物理媒体，绝不合并。
2. ReferenceAnchor retain：保留；它是 0.6.2 兼容的低层 ordered asset relation。
3. ReferenceSet replace ReferenceAnchor：不替换；ReferenceSet 是新建的可复用组合层，提供 Anchor adapter。
4. Multiple roles on Shot：允许；Character/Prop 用 role + ordinal，多实例不覆盖。
5. Dynamic resolve vs snapshot：编辑/预览/readiness 动态解析；Prepare/Start 冻结 Production Snapshot。
6. Reproducibility：冻结 profile revision、reference set revision、asset IDs/checksums、prompt、workflow、recipe、output spec 和 contextHash。
7. Profile edits affect old ProductionRun：不影响；已有 run/batch/snapshot 使用冻结输入；未准备的旧 shot 使用新 active revision。
8. Readiness frontend/backend：后端权威；前端只显示和做即时提示，不复制最终 gate。
9. Batch Preparation creates ProductionRun：默认不创建；只返回 plan，确认后创建现有 ProductionBatch；显式 Run 仍走既有 Orchestrator。
10. Auto Storyboard in 0.7.0：只做 P2 draft；人工确认前不得写正式 Shot、创建 batch 或生成。

全部十项架构决策均已确定，无悬而未决项。

## 11. Risks

- Schema complexity：最小表集，不存冗余 context。
- Duplicate ReferenceAnchor model：保留 Anchor，显式 adapter 到 ReferenceSet。
- Profile vs Asset confusion：UI/API 明确 physical 与 semantic。
- Prompt overgrowth：九段固定顺序、来源 trace、长度 gate。
- N+1：批量 resolver/readiness、set-based query、分页。
- UI complexity：沿用 C shell，Scene 三栏固定。
- Old compatibility：nullable 新关系、legacy path、不做人工 backfill。
- Queue coupling：Preparation 只 plan/add，唯一 start 仍由 Queue/Run 控制。
- Reproducibility：prepare/start 写 snapshot identity。
- Profile version drift：revision ID/hash 进入冻结输入。
