## 4. 核心产品问题与最终推荐

用户有 TXT、Markdown、JSON、小说或剧本时，目标是：

```text
原始文本
  → ScriptDocument
  → DraftStructure（Episode / Scene / Shot）
  → StoryboardDraft 与 Profile Match
  → 人工批量编辑/确认
  → 一次显式写入正式 Project Structure
  → 人工确认 Consistency Binding
  → ResolvedShotContext
  → Readiness / Preparation
  → 现有 ProductionQueue
  → ComfyUI
```

最终推荐是 **`ScriptDocument + DraftStructure`，而不是复制一整套正式 Series/Episode/Scene/Shot 表**：

1. ScriptDocument 保存输入来源、checksum、格式和定位；它不拥有生产身份。
2. DraftStructure 是可编辑的有序文档投影；它不拥有正式 Shot ID、Profile binding、workflow、batch、task 或 asset。
3. StoryboardDraft 作为 DraftStructure 的每镜建议，不独立成为执行模型。
4. 只有用户点击“确认写入正式结构”后，后端才在一个事务中创建正式层级并返回 ID mapping。
5. 确认后仍需由用户决定 Profile 关联；没有匹配时只能展示“建议创建新 Profile”，不能自动创建。

## 5. Script Import V1 规划

### 5.1 输入与输出

输入格式只承诺：

- TXT：按 UTF-8 文本、段落、空行和可识别标题做保守分块。
- Markdown：解析标题层级、列表、段落和代码块；代码块原样保留，不当作叙事指令。
- JSON：使用独立的 Script Import schema 和显式 `schemaVersion`，不得复用 H3、Workflow 或 Project Manifest JSON。

输出：

- `ScriptDocument`：原文/原文引用、format、filename、source checksum、parser diagnostics、source spans。
- `DraftStructure`：有序 `DraftEpisode → DraftScene → DraftShot`，所有节点使用 `draftNodeId`，不是正式数据库 ID。
- `StoryboardDraft`：每个 Draft Shot 的建议字段和来源引用。
- `DraftEntityMatch[]`：角色、场景、道具提及及候选 Profile 状态；未经确认没有正式 binding。

### 5.2 识别范围

解析器可以识别或建议：章节/集、场景、角色提及、对白、动作、地点、时间、心理描写和镜头候选信息。它必须保留“未识别/低置信度/冲突”诊断，不得声称小说能够被自动完美改编。

小说输入的处理策略是保守的：叙述文本成为 source block；对白保留说话者文本；心理描写标为 narration/thought cue；地点和时间变化提供 Scene boundary 候选；镜头由段落动作和空间变化生成低置信度建议。所有结果都进入 Draft，用户可编辑、合并、拆分和拒绝。

### 5.3 解析器边界

解析只做文本分析和结构建议，不做以下事情：

- 写 `production_series`、`production_episodes`、`production_scenes` 或 `shots`。
- 创建正式 Profile、ReferenceSet、Asset、Workflow、Batch、Task 或 Snapshot。
- 生成图片/视频、调用 ComfyUI、调用 Queue Start 或更改审核状态。
- 自动绑定高风险实体，或把 LLM 的 Profile ID 当作可信输入。

详细输入 contract、诊断和测试建议见 [SCRIPT_IMPORT_V1.md](architecture/SCRIPT_IMPORT_V1.md)。

## 6. Draft / Formal separation

### 6.1 状态

```text
IMPORTED
  → PARSED
  → DRAFT_EDITING
  → READY_FOR_CONFIRMATION
  → CONFIRMED_TO_FORMAL
```

节点可以有 `AI_SUGGESTED`、`PENDING_REVIEW`、`ACCEPTED`、`REJECTED`、`EDITED`、`CONFLICT`、`UNRESOLVED` 状态。`ACCEPTED` 只表示用户接受了 Draft 建议，不表示已经写入正式结构。

### 6.2 唯一正式写入边界

`script_draft_confirm`（名称在实现任务中冻结）是唯一允许 Draft 进入正式结构的 command/facade。它必须：

1. 接收 `projectId`、`draftId`、`draftRevision`、目标位置和明确的用户确认 token/版本。
2. 在服务端重新校验 Draft、目标 Project、节点层级、名称、ordinal 和冲突。
3. 一次事务创建或引用 Series/Episode/Scene，并创建 Shot 与 Scene assignment。
4. 返回 `draftNodeId → formalId` mapping、创建/跳过/冲突摘要。
5. 失败整体回滚；重复提交按 `draftId + draftRevision + projectId` 幂等或返回可解释的 already-confirmed。
6. 不调用 Profile binding、Readiness、Preparation、Queue、Generation 或 ComfyUI。

V1 默认 create-only：已有正式 Shot 不被覆盖；目标位置冲突必须让用户明确选择。确认前正式结构和 `shots` 行数必须保持不变。

## 7. Storyboard Draft V1

Storyboard Draft 是文本/画面建议层，不是 GenerationValues，不是 ProductionPlan，也不取代 `ResolvedShotContext`。

每个 Draft Shot 至少包含：

| 字段 | 语义 | 状态 |
| --- | --- | --- |
| Shot name | 镜头候选名称 | Draft text |
| Shot purpose | 叙事目的/信息 | Draft text |
| Character list | 角色提及和 match 引用 | 未确认 |
| Scene | 场景提及和 source span | 未确认 |
| Props | 道具提及和 match 引用 | 未确认 |
| Action | 动作建议 | Draft text |
| Dialogue | 对白引用/整理 | Draft text |
| Camera suggestion | 景别、角度、运动建议 | Draft text |
| Lighting suggestion | 光线/气氛建议 | Draft text |
| Duration suggestion | 时长建议 | Draft value，需校验 |
| Image prompt draft | 基础画面提示词草稿 | 非最终生产 Prompt |
| Video prompt draft | 基础视频提示词草稿 | 非最终生产 Prompt |

Storyboard Draft 不包含正式 Shot ID、asset ID、ReferenceSet binding、workflow、recipe、output spec、task、batch、生成结果或 Comfy 状态。正式生产时，最终 Prompt 仍由 Profile、Scene、Costume、Prop、Style、Shot Action、Camera、Lighting 和 Output Spec 经现有 PromptContextBuilder 构造。

详细字段、状态机和 UI 见 [STORYBOARD_DRAFT_V1.md](architecture/STORYBOARD_DRAFT_V1.md)。

## 8. Profile matching 与人工确认

匹配在后端使用项目隔离、ProfileType/角色类型隔离、名称规范化、显式 alias 和稳定排序的确定性函数；LLM 只提供 mention、别名或解释文本，不能决定最终 Profile ID。

| 状态 | 定义 | UI 动作 | 是否自动绑定 |
| --- | --- | --- | --- |
| `EXACT` | 项目内同类型唯一精确候选，或 Draft 已携带仍有效的候选引用 | 展示候选和匹配证据，用户确认/改选/忽略 | 否 |
| `LIKELY` | 没有精确命中，但只有一个可解释的候选 | 可预选，用户必须确认 | 否 |
| `NO_MATCH` | 没有符合项目和类型约束的候选 | 建议“创建新 Profile”或忽略 | 否 |
| `AMBIGUOUS` | 多候选、同分、类型不明或存在层级冲突 | 用户选择、保持未绑定或编辑提及 | 否 |

`selectedProfileId` 只有在用户明确确认后才具备写入意义；`LIKELY` 和 `AMBIGUOUS` 不得自动产生 binding。ReferenceSet、asset 顺序和 checksum 也不得从文本自动推断，必须在 Profile 确认后由用户选择或沿用已确认关系。

## 9. Script Import Workspace

入口放在既有 Creation workspace 下，不重做 StudioShell 或全局 rail。

```text
┌────────────────┬──────────────────────────────┬─────────────────────┐
│ 原文结构       │ 故事板草稿                   │ Draft Inspector     │
│ source blocks  │ Episode/Scene/Shot tree      │ fields/matches      │
│ spans/诊断      │ DRAFT 状态/筛选/批量动作      │ source/diagnostics   │
└────────────────┴──────────────────────────────┴─────────────────────┘
```

### 左栏：原文结构

展示文件格式、标题/段落/章节、行号或字符区间、原文片段、诊断、解析来源和被 Draft 节点引用关系。选择 source span 时，中栏跳转到对应 Draft 节点；左栏不能编辑正式结构、绑定或生产。

### 中栏：Draft Tree

显示 Episode → Scene → Shot 草稿树和明确的 `DRAFT｜尚未写入正式结构` 徽标。支持 Accept、Reject、Edit、Merge、Split、Reorder、批量 Accept/Reject、按状态/置信度/未关联 source/冲突筛选；这些操作只修改 Draft。

### 右栏：Inspector

显示节点层级、AI 原始建议、用户编辑值、source span、匹配候选、置信度/解释、校验错误、审阅状态和操作记录。Profile Match 需要明确的“关联已有 Profile / 建议创建新 Profile / 保持未绑定”选项；没有用户确认不能写正式 binding。

### 正式写入流程

```text
导入 → 解析 → 生成结构草稿 → 编辑/匹配 → 差异预览
                                      ↓
                         确认写入正式结构
                                      ↓
                    正式 IDs 返回；不自动绑定/生产/入队
```

提交前显示将创建的 Series/Episode/Scene/Shot 数量、拒绝节点、用户改动、未解决冲突和目标冲突。存在错误或未解决冲突时主按钮禁用；只有用户点击一次明确的“确认写入正式结构”才可提交。

详细 UX 和 UI 门禁见 [STORYBOARD_DRAFT_V1.md](architecture/STORYBOARD_DRAFT_V1.md)。

## 10. LLM 与 Offline / Provider Strategy

DEV-056 只冻结接口，不接入真实 Provider，不增加网络请求，不存 Provider secret。

推荐未来 seam：

```text
ScriptParser (deterministic, offline)
          │ optional text-analysis port
          ▼
DraftTextAnalyzer
  ├─ LocalLlmProvider
  ├─ OpenAiCompatibleProvider
  └─ UserConfiguredEndpointProvider
```

`DraftTextAnalyzer` 的输入是 ScriptDocument/source spans，输出是带 schema version、source spans、诊断和不可信文本的 `DraftPatch`。Provider metadata 至少需要 provider kind、model label、prompt contract version、input checksum 和 output checksum；它不能返回可信的 Profile ID、Asset ID、workflow 或执行请求。

推荐策略：

- 离线 deterministic parser 是默认可用路径，确保无网络也能得到 Draft。
- Local LLM 是未来可选能力，必须显式启用并标明模型版本。
- OpenAI-compatible/user endpoint 作为配置型适配器，不在 0.8.0 初始任务中真实接入。
- 所有 Provider 输出均须通过 schema、长度、source span 和安全校验；Provider 失败不能阻止用户继续编辑已有 Draft，也不能触发生产。

LLM 永远只负责文本分析、结构建议和 Prompt draft；ComfyUI 仍是唯一正式图片/视频生成执行引擎。

## 11. 最小持久化与候选 ERD

### 11.1 方案比较

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 全部 Draft 拆成 `draft_episodes/scenes/shots/matches` | 易于逐行查询 | 复制正式结构、迁移多、状态和 revision 容易漂移 | 不推荐 V1 |
| 只放 React 内存 | 最少代码、无 schema 变化 | 崩溃/跨会话/审阅恢复差，无法保留 source checksum 和 revision | 只适合一次性临时预览 |
| `ScriptDocument + DraftStructure` JSON 文档 | 结构自然、revision 易冻结、避免复制正式表 | 需服务端分页/虚拟化策略；全文查询不能依赖客户端全量渲染 | 推荐 V1 |
| JSON 文档加一张可选节点索引 | 可做分页/搜索 | 多一个派生索引，需要重建/一致性策略 | 规模门禁失败时再引入 |

### 11.2 最终推荐

V1 的持久化事实最少为：

1. `script_sources`：项目归属、格式、原始文件名、source checksum、原文存储引用、created/updated、不可变 source identity。原始文本不复制到每个 Shot。
2. `script_import_drafts`：`draft_id`、`project_id`、`source_id`、revision、parser/provider metadata、draft checksum、状态、summary counters、`payload_json`、前后 revision、created/updated/confirmed metadata。
3. `payload_json` 内包含 DraftStructure、StoryboardDraft、source spans、diagnostics、Profile Match 和人工操作后的当前投影；不另建 `draft_episodes`、`draft_scenes`、`draft_shots`、`draft_entity_matches` 表。

原始大文本优先放在应用管理的数据根并由 `script_sources` 引用；如果未来现有文件存储不能满足恢复，再在独立兼容评审中决定 source blob 字段。Draft payload 可以按 page API 返回，但 UI 不得一次渲染全部 5000 个节点。

如果 5000 Draft Shot 的分页/搜索基准证明读取整个 JSON 不可接受，后续 DEV-061/064 才可增加一张可重建的 `draft_node_index`；它是派生索引，不是第二套正式结构。任何新表都必须经过 migration、backup、manifest 和 upgrade 评审，不能在 DEV-056 偷渡 migration 025。

候选关系如下：

```text
script_sources (durable source metadata)
        │ 1:N
script_import_drafts (immutable revision metadata + payload_json)
        │
        ├─ DraftStructure: draft episode/scene/shot nodes
        ├─ StoryboardDraft: shot suggestions
        ├─ DraftEntityMatch: embedded match records
        └─ SourceProvenance: embedded spans and operation history

confirmed Draft
        │ explicit atomic promote
        ▼
production_series / production_episodes / production_scenes / shots
        │ user-confirmed binding only
        ▼
ResolvedShotContext → Readiness → Preparation Snapshot → Queue
```

## 12. Revision、Reparse、Diff 与 Provenance

- Source identity 由 `sourceId + sourceChecksum` 定义；同一文件内容不因文件名变化而误认为新内容。
- 每次解析产生不可变 Draft Revision；上一 Revision 仍可审阅、导出和回滚到 Draft 视图。
- 已人工编辑的节点保存原始 AI suggestion、当前 human value、source span 和 operation provenance。
- Reparse 产生新 Revision，按 source span、节点类型、邻近结构和 normalized text 生成 added/removed/changed/moved/uncertain diff；不能仅凭数组下标静默覆盖。
- 已经确认进正式结构的 Shot 不被 Reparse 覆盖。重新导入只产生新的 Draft 和影响预览；若要修改正式 Shot，用户必须走现有显式编辑流程。
- Draft Match 的候选变化会清除未确认的 selectedProfileId；已确认 binding 不被 Draft 自动改写。
- Formal promote 记录 `sourceId`、`draftRevision`、节点 provenance 和 `draftNodeId → formalId` mapping，不把完整原文复制到每个 Shot。

## 13. Narrative Preproduction V2 集成

V2 的职责是编排“文本草稿 → 人工确认 → 正式结构 → 0.7.0 生产准备”，不是新建生产系统。

| 阶段 | 所有者 | 允许的事实 | 明确禁止 |
| --- | --- | --- | --- |
| Script Import | Script parser / Draft service | source、diagnostics、Draft nodes | formal IDs、bindings、queue、Comfy |
| Storyboard Draft | Draft controller / optional text analyzer | shot suggestions、prompt draft、source provenance | final Prompt、GenerationValues、auto generation |
| Profile Match | deterministic matching service | candidates、status、evidence、user selection | automatic binding/profile creation |
| Formal Promote | ProductionPreparation-adjacent facade | formal structure IDs、mapping、provenance | overwrite existing Shot、auto binding、auto start |
| Context / Readiness | existing 0.7.0 services | formal Shot 的 resolved context、七 gates、preflight | Draft 直接 resolve/prepare |
| Preparation | existing service | server re-resolve、snapshot、batch admission | auto start、second queue |
| Execution | existing queue/generation/comfy | user-started image/video generation | second executor、unattended pipeline |

正式 Shot 创建后按以下顺序复用：

```text
formal Shot + confirmed bindings
  → existing ShotContextResolver
  → existing PromptContextBuilder
  → existing ShotReadinessService / Comfy preflight
  → existing ProductionPreparationService
  → existing ProductionQueueService
```

不要把 Storyboard 的 `imagePromptDraft` 或 `videoPromptDraft` 直接塞进 Queue；它们只能作为正式编辑时的输入参考。

完整的边界、接口 seam、Offline strategy、audit 和性能方案见 [NARRATIVE_PREPRODUCTION_V2.md](architecture/NARRATIVE_PREPRODUCTION_V2.md)。

## 14. 大剧本性能目标

规划容量是 100 Episodes、1000 Scenes、5000 Draft Shots，不代表一次正式生产 5000 Shot。

必须满足：

- Source 解析支持进度、取消和明确错误，不静默截断。
- Draft API 支持按 revision、Episode、Scene、status、search 条件分页；返回 `total`、`hasMore` 和稳定 cursor/ordinal。
- Draft Tree 对扁平可见节点采用 virtualization 或分层懒加载；Inspector 只加载当前 node。
- 原文视图按 source block/viewport 窗口化；不因 5000 节点全量 DOM 阻塞输入。
- 选择、焦点、source span 和筛选跨页保持稳定。
- Confirm 允许按用户选择批量提交，但后端仍是一项事务；不把 5000 Draft Shot 自动变成 5000 个生产任务。
- 正式 Production 继续沿用 0.7.0 的 500 Shot 等既有 batch/resolver limits。

目标门禁在 DEV-057/061/064 实测，不在 DEV-056 虚构性能数字。

## 15. 兼容性与安全边界

- 0.7.0 项目可以直接打开；旧项目不需要 ScriptDocument，也不需要生成空 Draft。
- Script system 是 optional；没有 Script source 的旧 Shot 继续走 legacy path、现有 context、readiness 和 queue。
- 不修改 migration 024、Backup 14 或 Manifest 2；未来 Draft 持久化若需要 migration，必须单独通过 upgrade/backup/manifest gate。
- Provider 配置不进入正式生成输入，不把 API key、完整原文或 provider response 复制到 Shot。
- 项目隔离、source checksum、文件大小/编码/JSON schema、payload schema version、权限和路径边界必须后端校验。
- 不信任 LLM 输出的 HTML、命令、URL、Profile ID、Asset ID、workflow ID 或 JSON 任意字段。
- 拒绝/撤销/重排/合并/拆分只影响 Draft；正式写入有差异预览、幂等和全量回滚。

## 17. 验收总门禁

### Draft 安全

- TXT、Markdown、JSON 都只产生 Draft。
- Import/parse/analyze 前后正式四类结构表和 `shots` 行数不变。
- AI/LLM 结果标为 DRAFT，不能创建 Profile、binding、Batch、Task、Snapshot 或 Comfy 请求。
- Draft 的 Accept/Reject/Edit/Merge/Split/Reorder 可撤销或产生新 revision。

### 正式晋级

- 提交前显示 diff、数量、目标和冲突；未解决项禁用提交。
- 唯一显式 Confirm 才能创建正式层级。
- Confirm 是单事务，失败全回滚，重复提交可解释且不重复创建。
- 已有正式 Shot 默认不覆盖；source provenance 和 draft-to-formal mapping 可查询。

### 一致性与生产

- Profile Match 四状态覆盖项目隔离、类型隔离、同分冲突和 stable order。
- Profile/ReferenceSet 只在人工确认后进入现有 bindings。
- Formal Shot 只复用现有 Resolver、PromptContextBuilder、Readiness、Preparation、Snapshot 和 Queue。
- Queue Start、候选选择、审核和重生成继续是 Manual Gate；ComfyUI 仍是唯一正式执行引擎。

### 规模与兼容

- 100 Episodes、1000 Scenes、5000 Draft Shots 有 fixture、分页/虚拟化、内存和输入响应门禁。
- 不一次返回或渲染 5000 个完整正式 `ShotView`。
- 0.7.0 项目无 ScriptDocument 仍能打开和生产；现有 migration 024、Backup 14、Manifest 2 不变。
- 无 migration 025、第二执行器、第二队列、Scheduler、自动选片或无人值守生成。

## 18. 明确延期到 0.9+

0.8.0 不做：

- 全自动导演、自动生成整集或无限 Agent 自主循环。
- 自动选择图片、自动批准视频、自动运行 Queue、Auto-next。
- Script → 正式 Shot 的无确认自动覆盖。
- DOCX/PDF/复杂自然语言全自动改编承诺。
- 云端同步、登录、多人协作、模型训练、LoRA、插件市场。
- StoryboardExecutor、ScriptProductionQueue、AIProductionScheduler、AutoGenerationPipeline 或第二 ProductionRun。

这些能力如有必要，只能在 0.9+ 重新立项并重新评估人工安全边界。
